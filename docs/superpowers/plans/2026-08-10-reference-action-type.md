# Reference Action Type (API) Implementation Plan

> **For agentic workers:** execute task-by-task with a review after each task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Gundi API accepts integration-type registrations containing actions with `"type": "reference"`, keeps those actions out of per-integration configuration rows, and (verified by tests) already authorizes config editors to invoke them through the existing execute proxy.

**Architecture:** `IntegrationAction.type` is a Django `TextChoices` CharField; DRF serializers derive their `ChoiceField` from it automatically, so ask 1 of the RFC (`gundi-integration-cmore/docs/rfc-reference-data-portal-support.md`) is one enum member + migration. Ask 2 needs **no code**: the execute proxy (`ActionTriggerView.execute`) has no `is_executable` or type gate — authorization is org-admin/superuser, the same tier required to edit configuration — so we pin that contract with tests. We additionally skip reference actions in the type-blind config backfill, since reference actions are stateless and their config rows would be junk shown to operators.

**Tech Stack:** Django 3/4 + DRF, pytest-django. Work happens in an isolated worktree off `origin/main` (the main checkout has unrelated in-progress work).

## Global Constraints

- All paths relative to the worktree root; the Django project is `cdip_admin/`.
- Follow existing test style in `cdip_admin/api/v2/tests/` (pytest fixtures from `conftest.py`, `requests_mock` + mocked `google.oauth2.id_token` for the runner call — see `test_actions_execution_api.py`).
- Run tests with the repo's venv from `cdip_admin/`: `../.venv/bin/pytest <paths>` (adjust to the actual venv path discovered during setup; if the repo uses a different runner, e.g. `pytest.ini`/`manage.py test`, follow it).
- Migration must be generated by `makemigrations`, not hand-written.

## Key verified facts

- Enum: `cdip_admin/integrations/models/v2/models.py:57-66` (`ActionTypes`: auth/pull/push/generic; `type = CharField(max_length=20, choices=..., default=GENERIC)`).
- Registration: `POST /v2/integrations/types/` → `IntegrationTypeIdempotentCreateSerializer` (`api/v2/serializers.py:402-477`); nested `IntegrationActionCreateUpdateSerializer` (`:365-382`) exposes `type` as a plain ModelSerializer field → auto ChoiceField from model choices.
- Execute proxy: `ActionTriggerView` (`api/v2/views.py:577-600`), route `POST /v2/integrations/{integration_pk}/actions/{value}/execute/`; permissions `IsSuperuser | IsOrgAdmin | IsOrgViewer`; `IsOrgAdmin.org_admin_allowed_actions = {"actions": ["execute"], ...}`; viewers denied on non-safe methods. No type/is_executable inspection anywhere.
- Config backfill is type-blind: `Integration.create_missing_configurations` (`integrations/models/v2/models.py:401-415`) iterates all type actions; `IntegrationAction._post_save` (`:146-156`) schedules `backfill_action_configurations_for_type` (`integrations/tasks.py:429+`) unconditionally.
- Pre-existing bug: `IntegrationTypeIdempotentCreateSerializer.validate()` (`api/v2/serializers.py:429-437`) references `action` before assignment on the update path (`if self.instance and "value" in action:` — should be `action_data`) and passes `integration_type=self` (the serializer) instead of `self.instance`. Fires on any PATCH/PUT to `/v2/integrations/types/{value}/` whose payload includes `actions`. Untested today.

### Task 2: keep reference actions out of per-integration configurations

**Files:**
- Modify: `cdip_admin/integrations/models/v2/models.py:401-415` (`create_missing_configurations`)
- Read + modify if needed: `cdip_admin/integrations/tasks.py:429+` (`backfill_action_configurations_for_type` — if it passes an unfiltered action list or queries independently, apply the same exclusion at its query)
- Test: `cdip_admin/integrations/tests/test_signals.py`

**Interfaces consumed:** `ActionTypes.REFERENCE` from Task 1.

- [ ] **Step 1: Write the failing tests** — in `test_signals.py` style (see `test_new_action_backfills_existing_integrations:28`): create an integration of a type, then add a *reference-typed* `IntegrationAction` to the type; run the backfill (however the existing test triggers it — signal with eager celery or direct task call) and assert **no** `IntegrationConfiguration` row is created for the reference action, while a simultaneously-added generic action **does** get one.
- [ ] **Step 2: Run — expect FAIL** (a row IS created today).
- [ ] **Step 3: Implement** — in `create_missing_configurations`, replace the default query:

```python
        if actions is None:
            actions = self.type.actions.all()
        # Reference actions are stateless queries (config model IS the query);
        # they have no per-integration configuration, so don't create junk rows
        # that would surface in the portal's configuration list.
        actions = [a for a in actions if a.type != IntegrationAction.ActionTypes.REFERENCE]
```

(Filtering the materialized list keeps the caller-supplied `actions=` optimization intact. If `backfill_action_configurations_for_type` builds its own queryset, add `.exclude(type=IntegrationAction.ActionTypes.REFERENCE)` there too.)
- [ ] **Step 4: Run the signal/backfill tests** — `pytest integrations/tests/test_signals.py -q` plus the full `integrations/tests/`. Expect PASS.
- [ ] **Step 5: Commit** — `feat: skip reference actions in per-integration config backfill`.

### Task 3: fix `validate()` NameError on integration-type updates with actions

**Files:**
- Modify: `cdip_admin/api/v2/serializers.py:425-437`
- Test: `cdip_admin/api/v2/tests/test_integrations_api.py`

- [ ] **Step 1: Write the failing test** — as superuser, `PATCH /v2/integrations/types/{value}/` (mirror `test_update_service_url_in_integration_type_as_superuser:811` setup) with a payload containing `actions: [{"type": "reference", "name": ..., "value": <existing-or-new slug>, "schema": {...}}]`; assert it does not 500 and the action is upserted.
- [ ] **Step 2: Run — expect FAIL** with `NameError: name 'action' is not defined` (or 500).
- [ ] **Step 3: Implement** — fix the loop body:

```python
        for action_data in data.get("actions", []):
            if self.instance and "value" in action_data:  # Update path
                action = IntegrationAction.objects.filter(
                    integration_type=self.instance, value=action_data["value"]
                ).first()
                serializer = IntegrationActionCreateUpdateSerializer(
                    instance=action, data=action_data
                ) if action else IntegrationActionCreateUpdateSerializer(data=action_data)
            else:  # Create
                serializer = IntegrationActionCreateUpdateSerializer(data=action_data)
            serializer.is_valid(raise_exception=True)
```

(`.filter().first()` instead of `.get()`: an update payload may introduce a brand-new action value — validate it as a create rather than 404.)
- [ ] **Step 4: Run** — the new test + `pytest api/v2/tests/test_integrations_api.py -q`. Expect PASS.
- [ ] **Step 5: Commit** — `fix: integration-type update with actions payload no longer raises NameError`.
